# purescript-jtms — library design sketch

*2026-07-15, the session after the bettor. Extracted-from and motivated-by
kibitzer (Marginalia #251); the design record that led here is
`kibitzer/docs/smt-jtms-brainstorm.md` (the ⊢/⊨ correspondence and the
client hunts) and `kibitzer/docs/bayesian-layer.md` (the P column and why
it stays out of this library).*

**Status (same evening):** kernel v0 and the Sudoku client are built
and tested — see the README for the workspace shape. The kernel
followed layer 1 below almost verbatim (`Why = Axiom | ByRule`; the
hash-consing index doubles as the premise lookup; `explain` is a
single backward scan exploiting acyclicity-by-construction). Not yet
started: the eDSL (rules are prim-form only), perspectives, the
oracle/test-kit package, all-justifications recording.

**On the name**: deliberately plain, and a working name only. Andrew's
rule: don't call it a JTMS in public unless it *is* a full JTMS —
Doyle's non-monotonic labelling and all — which v1 deliberately is not
(see the extensions catalogue). Rename before publication. Candidate
with some support: **Baskerville** — the Haskell propagator world
already has `holmes`; we'd be the casebook.

## Thesis

A justification-propagating inference engine as a standalone PureScript
library, where **the explanation is the product**. Every fact in the
knowledge base is a proof term — it carries the rule that derived it and
the facts it consumed — and the primary consumer-facing artifact is the
derivation DAG: renderable (kibitzer's cascade/orbits/skylines),
queryable (`explain`), and testable against an outside oracle.

The niche is genuinely unoccupied. The propagator lineage this sits in —
Radul & Sussman's networks, Kmett's `propagators` and `guanxi`, Tom
Harding's `holmes` — points the same lattice-and-monotone-functions
machinery at *search*: solve Sudoku, find satisfying assignments, learn
nogoods. Provenance exists in those systems as internal fuel for the
backtracker. Nobody ships the derivation DAG as the deliverable. That is
the whole kibitzer lesson: the notebook people want to look at is the
*why*, not the answer.

## What kibitzer already proved (the extraction source)

The prototype kernel is `kibitzer/core/src/Kibitzer/{Knowledge, Infer,
Observe, Cascade}.purs`. Read with library eyes, it has already made the
key moves:

- **Facts are proof terms.** `Justification = { rule, source, origins,
  premises }` is a defunctionalised rule application — the instruction
  functor of inference, reified. (The Faubion "Free From Tree" move,
  applied to derivation instead of sequencing: the knowledge base is the
  free algebra generated by rules-as-constructors over observation
  axioms.)
- **First-justification-wins is hash-consing.** `addFact`'s dedup is
  what turns the free *tree* (every proof spelled out, exponentially
  redundant) into the shared *DAG* the cascade draws. Premises point
  backwards by FactId issue order, so acyclicity is by construction.
- **Saturation is a Kleene fixpoint.** Monotone rules on finite claim
  universes; termination by "a pass that changes nothing is the
  fixpoint". Not free-anything, and shouldn't be — its principled home
  is the Datalog/propagator tradition.
- **Rules are already data.** `allRules :: Array (Knowledge -> Array
  Derived)` — opaque functions, but an array of them, with fixed order
  as observable spec.
- **Perspectives are observation projection.** One rule set, many minds;
  the watcher and each player fold the same `learn` over different
  streams. The player-⊇-watcher monotonicity theorem is a library-grade
  property.
- **Completeness is measurable from outside.** The Z3 differential
  oracle (and the bettor's discovery that for finite universes the ⊨
  side is *pure counting*, no solver needed) gives the library a
  shippable test kit, not just a test suite.

Acceptance test for the extraction: kibitzer-core rebuilt on the
library, golden feed tests unchanged.

## The layer stack

### 1. Proof-term kernel

```purescript
newtype FactId = FactId Int

type Fact claim rule ax =
  { id :: FactId
  , claim :: claim
  , why :: Why rule ax
  }

data Why rule ax
  = Axiom ax                     -- observed, not derived
  | Derived
      { rule :: rule
      , premises :: Array FactId
      , anchors :: Array ax      -- kibitzer's source/origins, generalised:
      }                          -- non-fact provenance (events, timestamps)

explain :: forall claim. Ord claim => KB claim -> claim -> Maybe (DerivationDag claim)
```

`claim`, `rule`, and `ax` are all user types. The kernel owns FactId
issue, the hash-consed feed, acyclicity, and DAG extraction. Everything
kibitzer's Cascade module computes (frames, depths, edges) generalises
here.

### 2. Rule eDSL + escape hatch

Two tiers, deliberately:

**eDSL rules** — bodies in a free applicative/alternative over a `Match`
functor (conjunctive queries with enumeration, stratified negation, and
aggregation):

```purescript
rule "envelope-by-elimination" do
  c <- each allCards
  traverse_ (\p -> require (Lacks p c)) allPlayers
  conclude (InEnvelope c)
```

Interpreting the structure *without running it* yields the rule's
read-set (which claim shapes it consumes). Three things fall out of that
one analysis: semi-naive evaluation (only re-fire rules whose reads
intersect the delta), stratification checking, and the rule-wiring
diagram for free.

**Prim rules** — the escape hatch that keeps the eDSL small:

```purescript
primRule ::
  { name :: String
  , reads :: Array (ClaimPattern claim)   -- declared by hand, NOT inferred
  , fire :: kb -> Array (Derived claim)   -- arbitrary PureScript
  } -> Rule kb claim
```

The invariant moves from the interpreter to the author: an
under-declared `reads` means the rule silently fails to re-fire and the
KB is *incomplete with no error anywhere*. Two mitigations, both already
proven in kibitzer: (a) the differential property `saturate semi-naive ≡
saturate naive` catches read-set lies on random instances; (b) the ⊨
oracle bounds completeness from outside regardless. Provenance inside a
prim rule is the author's job and may be honestly partial —
`DisjunctionCapacity`'s precedent: "an anchor for the arcs, not a proof
term."

Calibration from the prototype: of kibitzer's nine rules, roughly six
are eDSL-shaped; `DisjunctionCapacity` (disjoint-family search) and
arguably `DisjunctionPigeonhole` are hatch material. Most rules pretty,
the combinatorial monsters escape-hatched but still scheduled and
tested — that ratio is the design working.

**The hatch's poster boy: Régin's alldifferent (1994).** The most
famous algorithm-inside-a-rule in constraint programming: an
alldifferent constraint induces a bipartite variables↔values graph;
build a maximum matching and prune every edge in no maximum matching —
a full graph algorithm (matching + SCC decomposition) as one inference
step, constitutionally inexpressible in a conjunctive-query eDSL. This
is why real CP solvers have exactly our two-tier architecture
(declarative constraints + "global propagators" that are arbitrary
algorithms): the hatch is the industry's load-bearing wall, not an
apology. It lands on both existing clients — Sudoku's rows/columns/
boxes are alldifferents, and the fish patterns and hidden subsets are
shadows of matching-based filtering; kibitzer's `DisjunctionCapacity`
is a hand-rolled Hall's-theorem special case groping toward it. And it
upgrades the provenance story: Régin's prunes carry *real
certificates* — every pruned edge is witnessed by a Hall set (k
variables spanning only k values, extractable from the SCCs) whose
member facts are honest premises. So prim-rule provenance is graded:
**certificate-producing** where the algorithm admits a witness,
anchor-only where it doesn't.

### 3. Perspectives

Generalise `Observe`: a perspective is a projection of the event stream;
minds are folds of `learn` over projected streams; the library ships the
monotonicity property ("a mind that saw strictly more derives a
superset") as a reusable law, QuickCheck-style.

### 4. Oracle seam + test kit

```purescript
explainOr :: KB claim -> claim -> Either UnsatCore (DerivationDag claim)
```

The seam where ⊢ meets ⊨. The test kit ships: (a) the differential
saturation property; (b) a generic finite-universe model enumerator (the
bettor taught us this is counting, not solving — no Z3 dependency in the
library) so any client can measure its completeness gap the way kibitzer
measured the watcher's; (c) the perspective-monotonicity law.

## The carrier: sets vs. lattices (the fork)

Is the KB **(a)** a set of claims (Datalog-shaped: `Ord claim => Set
claim` + the feed), or **(b)** an information lattice (propagator-
shaped: cells whose values refine monotonically)?

Kibitzer needs (b): a disjunction's candidate set shrinking {a,b,c} →
{a} is monotone in the *information order*, not set inclusion. And the
tell that (b) is right: Harmonia's scale inference is the same shape —
candidate keys are a disjunction that notes prune, and "the tonic is D"
is a `SingletonDisjunction` firing. ShapedSteer is happy with (a), which
is just the powerset instance of (b).

**Recommendation**: carrier = join-semilattice of information states,
with proof-carrying *increments*. Claims are the join-irreducible atoms
that get FactIds and justifications; disjunction-like residues are
lattice values that shrink between them. The subtle bit to design
carefully: what earns a FactId when a lattice value refines but no atom
crystallises (a disjunction dropping from 3 candidates to 2)? Kibitzer's
answer — residues are auxiliary, only atomic claims get proof terms,
resolution cites the pruning facts — worked well and is the v1 answer.

## Extensions catalogue

Sized on utility / implementation cost / ease-of-use penalty. Order ≈
when they'd land.

| # | Extension | Utility | Impl cost | Ease-of-use penalty | Verdict |
|---|---|---|---|---|---|
| 1 | Windowed/temporal rules | High (Harmonia counterpoint; any stream client) | Low as sugar | Low–moderate | **v1, via timestamped claims** |
| 2 | Stratified negation + aggregation | Mandatory (Cluedo itself needs it) | Moderate | Low | **not optional — core** |
| 3 | Record *all* justifications | Moderate now, high later | Low | None | **v1, cheap door-opener** |
| 4 | Retraction by replay | High (counterfactuals) | Near zero | None | **v1 — it's a function we have** |
| 5 | Semi-naive/incremental engine | High for real-time | Moderate, contained | None (invisible) | v1.5, needs #2's read-sets |
| 6 | Doyle's full non-monotonic JTMS | Real but narrower than it looks | **High** | **High** | someday; mostly defused by #4 |
| 7 | ATMS labels (de Kleer) | High conceptually (the ⊨ bridge) | High (exponential labels) | Low (query-side) | someday; #3 keeps the door open |
| 8 | First-order claims / unification | Unclear — no client needs it | High | Moderate | **explicitly out: finite universes** |
| 9 | Weighted/soft rules | Tempting, wrong layer | Slippery | High (semantics blur) | **out of kernel — P lives over models** |

The argued ones:

**#1 Windows.** The insight that keeps this cheap: *forgetting* breaks
monotonicity, *timestamps* don't. Parallel fifths is a join on adjacent
beat indices — `Motion beat pair kind interval` claims, rule matches
`beat` and `beat+1` — an ordinary conjunctive query on a monotone KB;
the termination argument is untouched. v1: claims carry time indices
where the domain has time; the eDSL grows `window`/`adjacent` as pure
sugar over index joins. Penalty: index plumbing in claim types —
visible but idiomatic. The expensive version (bounded memory, facts
expiring from a sliding window, for a rig running hours) is genuine
forgetting — a cousin of #6 — and linting a piece or a session doesn't
need it. Deferred, explicitly.

**#6 Doyle in full.** What it adds: justifications with out-lists
("believe X if A is in and B is *out*") — defaults and assumptions —
plus the in/out labelling algorithm and dependency-directed
backtracking. Utility is real (ShapedSteer "assume the estimate until
measured"; Harmonia "assume the key holds until modulation evidence"),
but the costs are structural: the labelling algorithm has genuine
subtleties (odd loops, unfounded support), retraction destroys the
append-only feed so "facts are proof terms" becomes "proof terms
currently in force", termination needs a new argument, and the cascade
would have to draw belief being *withdrawn*. Worst ease-of-use row in
the table: users must reason about non-monotonic loops in their own
rule sets. And two cheaper rows eat most of its lunch: #4 (retract an
observation by replaying the log without it — `knowledgeTimeline`
already is this machine, milliseconds at our KB sizes) and #2 (much
practical default reasoning is "conclude X when no evidence of Y",
which stratified negation handles monotonically). Catalogued with
respect; sequenced last; Doyle-completeness is a research milestone,
not a client need. It is also the *naming gate*: the public name must
not claim JTMS unless this row lands.

**#7 ATMS.** Labelling every fact with the assumption-sets under which
it holds is the ⊢ side's native bridge to the worlds pages — the
bettor's enumeration *is* an extensional ATMS. Full labels blow up
exponentially, but #3 (keep every justification instead of first-wins —
a one-line change to the dedup, append rather than drop) costs nothing
now and makes ATMS retrofittable rather than a rewrite.

**#8 and #9 — the two "no"s that shape the library.** Finite,
enumerable claim universes is what all three clients actually have (21
cards; 12 pitch classes × small windows; the nodes of a given DAG), and
it keeps rules as honest enumerations rather than a unification engine.
Soft rules stay out because the bettor already located probability: not
in the derivation engine but *over the model space* — P is a measure on
worlds, not a decoration on rules. The trinity stays three columns.

## The three clients

Design against all three from day one; each stresses a different layer.

### kibitzer (exists — the extraction source)

- **claims**: `Holds p c | Lacks p c | InEnvelope c | NotInEnvelope c`;
  universe ≈ 21 cards × (players + envelope) ≈ 300 atoms.
- **residues**: shown-card disjunctions (candidates shrink, resolve).
- **rules**: nine; six eDSL-shaped, the capacity/pigeonhole pair via the
  hatch. Needs negation ("no player holds c") and counting ("all but
  one excluded") — hence #2 is core.
- **stresses**: perspectives (watcher vs players), golden feed
  stability (rule order is observable spec), the cascade renderer as
  the DAG consumer.

### Harmonia (scale inference + counterpoint linting)

- **claims (inference)**: `NoteHeard pc t | TonicIs pc | ModeIs m |
  Diatonic pc | Chromatic pc` — candidate scales/keys as the residue,
  pruned by heard notes; "tonic is D" is `SingletonDisjunction`
  firing. Kibitzer-isomorphic, which is the point.
- **claims (linting)**: `Motion beat pair kind interval`, verdict
  claims like `ParallelFifths beat pair` — windowed joins (#1), every
  lint verdict carrying the derivation that names the offending beats.
- **stresses**: timestamped claims, the window sugar, and the real-time
  argument — monotone saturation per MIDI event, no search, no
  backtracking, so the rig could conceivably run it live. Semi-naive
  (#5) is what makes that honest at tempo.

### ShapedSteer (plan facts + the build system)

- **claims**: `Ready node | Blocked node | Stale node | UpToDate node
  | InputChanged edge` etc., over the nodes/edges of a given workbench
  graph — the powerset instance of the carrier.
- **the build-system angle** (Andrew, 2026-07-15: strongly motivating):
  Build Systems à la Carte factors a build into scheduler × rebuilder;
  the JTMS slots in as the *rebuilder's evidence store*, with `explain`
  answering "why did this rebuild" — the perennial most-wanted feature
  of every build tool (Shake grew a reporting subsystem for it). The à
  la carte port already lives in `purescript-ports`. Self-hosting in
  the best way: ShapedSteer renders derivations, so staleness proofs
  become things you look at in the graph view.
- **stresses**: `explain` as UX, and retraction-by-replay (#4) — graph
  edits invalidate observations, replay is the natural response.

### The PureScript registry solver (aspirational, real)

`purescript/registry-dev` ships `Registry.Solver` as a reusable
PureScript library — a PubGrub-shaped, PureScript-native version
solver whose community has already identified explanation quality as
the hard part (Verity Scheel, "The Best Errors for Solving Dependency
Versions"). The honest contribution shape is not replacing the solver
but being *the provenance layer a solver reports through*: candidate
versions as residues, constraint propagation as prunes-on-the-feed,
failure narratives as derivation DAGs.

- **claims**: `Excluded pkg version | Pinned pkg version |
  RangeNarrowed pkg range`; residue = live candidate-version set per
  package.
- **stresses**: prune-facts at scale, and the finite-universe
  assumption (version sets are finite but large — the first client
  that might make #8 or indexing earn their keep).

## Demos — one per layer

The demo suite should map demos to the layers they exercise, not pile
everything into one:

- **Sudoku** (in-repo example) — kernel + eDSL + prune-facts. Cliché
  as a solver, virgin as an *explainer*: every eliminated pencil mark
  carries its derivation. Zero domain teaching (the library is the
  only new thing on screen); human rule names (naked single, hidden
  pair, pointing pair, X-wing) are rules-as-data with built-in grading
  — the rule tier needed to crack a puzzle is its difficulty, so the
  rule set is a difficulty grader. Monotone saturation solves exactly
  the no-search subset; the bundled ⊨ enumerator solves everything;
  the gap between them replays kibitzer's watcher-vs-Z3 story in a
  domain everyone knows, and "this puzzle requires guessing" becomes a
  theorem the library proves about itself. Singles/pairs are
  eDSL-shaped; fish patterns deliberately stress the hatch boundary —
  and the hatch's poster boy (Régin's alldifferent, above) subsumes
  the whole fish/subset family, enabling the demo's best page: with
  all-justifications recording (#3), one pencil-mark prune arrives on
  the feed twice — "X-wing on rows 3/7" from the human-tier eDSL rule
  and "in no maximum matching, Hall set {…}" from the prim rule — the
  two tiers proving the same fact in different vocabularies.
- **kibitzer** — perspectives (stays the flagship, in its own repo;
  acceptance test = core rebuilt on the library, goldens unchanged).
- **Harmonia** — windows + the tonal-ambiguity meter.
- **registry-index re-solving** — the real-world PubGrub story: feed
  the locally-cloned `registry-index` manifests to a JTMS-backed
  solve and emit "why was 2.3 excluded" narratives for actual
  packages. A demo over real registry data is worth ten toys.

## Neighbours: hylograph-graph

No overlap by design — hylograph-graph is algorithms *on* graphs, this
library is justified facts (which sometimes concern, or produce,
graphs) — but the two should be comfortably compatible, and the seams
are concrete:

1. **Prim rules call it.** The Régin poster boy needs bipartite
   machinery + SCC decomposition, and hylograph-graph already ships
   `stronglyConnectedComponents` and `detectBipartite`; the one
   missing ingredient, maximum bipartite matching (Hopcroft–Karp),
   belongs in hylograph-graph rather than here. The flagship
   escape-hatch rule is thereby a composition demo: the inference
   library's hardest rule implemented by calling the graph library.
   Both sides are pure functions over `Ord node` — the same purity
   discipline as `fire`, so they compose with no adapter layer.
2. **The derivation DAG exports as `SimpleGraph FactId`** (plus a
   payload map). Then all of hylograph-graph applies to proof
   structures for free: `sugiyamaLayout` draws cascades,
   `transitiveReduction` declutters redundant premise edges in dense
   derivations, `reachableFrom` answers "everything downstream of
   this axiom". Kibitzer's orbits/skylines already prove
   proof-DAGs-as-graph-data pays; make the conversion one function.
3. **Graphs as axiom sources.** The ShapedSteer client runs the other
   direction: hylograph-graph calls in observation position generate
   axiom facts *about* a workbench graph (reachability, cycles,
   topological layers), which the rules then reason over.

## Non-goals (v1)

- Doyle's non-monotonic labelling and retraction (#6) — and therefore
  the public name "JTMS".
- Unification / infinite claim universes (#8).
- Probabilistic weights in the kernel (#9) — the P column composes from
  outside, over the model enumeration, as the bettor demonstrated.
- Bounded-memory streaming (true forgetting).

## Open questions

1. ~~The FactId-vs-residue boundary in the lattice carrier~~ —
   **resolved 2026-07-15, same evening: prune-facts are client
   policy, not a kernel decision.** The lattice-increment framing
   makes an atom crystallising and a candidate dying the same kind of
   thing (a proof-carrying increment); the client declares which
   increments earn a FactId on the feed. Evidence both ways: Andrew's
   own musical avenues (ambiguity, bitonality, dissonance) want the
   *unresolved residue itself* as the product — the live candidate
   set as a renderable object, log₂(candidates) as a tonal-ambiguity
   meter in bits, with per-window residues (extension #1) letting
   ambiguity re-bloom across phrases — and no prune narrative at all.
   Meanwhile the prune-facts-on-the-feed clients are legion, with one
   famous existence proof: PubGrub (Dart's version solver), whose
   celebrated feature is compiling the prune trail into human-readable
   failure derivations. Also: compiler candidate resolution ("candidate
   not viable because…"), differential diagnosis (de Kleer's ATMS home
   turf), fault localization/bisection, explainable puzzle solvers
   (pencil-mark elimination), and kibitzer's own cascade brackets,
   whose shrinks currently have no DAG edges and whose prune moments
   are exactly where the entropy chart's bits land.
2. How much of `Match` is applicative vs monadic: variable binding via
   pattern functors keeps analyzability; where exactly does the
   Cluedo/Harmonia rule corpus force value-dependent matching?
3. Does the perspective layer generalise cleanly when observations
   aren't a shared total-order stream (Harmonia's linter sees a score,
   not a log)? Possibly perspectives are just "which axioms you got" —
   the stream is kibitzer-specific.
4. Repo shape: single package or core + test-kit split (the enumerator
   and QuickCheck laws pull in dependencies the kernel shouldn't have)?

## Prior art shelf

- Jon Doyle, *A Truth Maintenance System* (1979) — the JTMS proper.
- Johan de Kleer, *An Assumption-based TMS* (1986) — the labels.
- Jean-Charles Régin, *A filtering algorithm for constraints of
  difference in CSPs* (1994) — the poster-boy global propagator; the
  precedent for algorithm-shaped rules with certificate provenance.
- Radul & Sussman, *The Art of the Propagator* (2009) — cells, monotone
  merge, provenance as motivating payload.
- Kmett: [propagators](https://github.com/ekmett/propagators) (talk
  companion, observable sharing),
  [guanxi](https://github.com/ekmett/guanxi) (propagators + CDCL as a
  logic-programming substrate).
- Tom Harding, [holmes](https://hackage.haskell.org/package/holmes) —
  the shipped reference: join-semilattice cells + CDCL, aimed at
  search.
- Datalog: naive/semi-naive evaluation, stratified negation — the
  engine's semantics.
- Arntzenius & Krishnaswami, *Datafun* — monotonicity in the types; the
  north star we don't need to reach.
- Nate Faubion, *Free From Tree* — the defunctionalisation move, here
  applied to derivation (kernel, already done in kibitzer) and matching
  (rule eDSL, the new work).
