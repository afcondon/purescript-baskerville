# An introduction to justified inference

*For programmers who know PureScript or Haskell, but not truth
maintenance systems. Everything here is grounded in the library's
actual types; the modules referenced are `Baskerville.Kernel`, `Baskerville.Engine`,
`Baskerville.Rule`, `Baskerville.Explain`, and `Baskerville.Testkit`.*

## The problem: answers without reasons

Most inference machinery — constraint solvers, Datalog engines,
type-class resolution, your own hand-rolled "keep applying rules until
nothing changes" loop — has the same shape: facts go in, consequences
come out, and the consequences are *bare*. The output is a set. Ask
the solver "why is this true?" and it shrugs; the reasoning was real,
but it happened in the call stack and the call stack is gone.

Usually that's fine. Sometimes the *why* is the entire point:

- A Sudoku assistant that says "the 4 goes here" is a spoiler. One
  that says "the 4 goes here **because** the other eight digits are
  eliminated in this cell, and here is why each of them is" is a
  teacher.
- A build system that rebuilds a target is doing its job. One that can
  answer "why did this rebuild?" is answering the most-asked question
  in the history of build tools.
- A dependency solver that fails with "no valid assignment" is
  useless. One that walks you through the chain of exclusions that
  cornered it (this is PubGrub's celebrated feature, in Dart's `pub`)
  is actionable.

The classical AI literature solved this in the late 1970s under the
name **truth maintenance systems** (TMS): Jon Doyle's JTMS
(justification-based, 1979) and Johan de Kleer's ATMS
(assumption-based, 1986). The core move is simple and typed-FP-shaped:
**don't record beliefs — record beliefs paired with the reason you
hold them.** Every derived fact carries a *justification*: the rule
that produced it and the facts it consumed. Doyle wanted this so a
program could efficiently *retract* beliefs when their support
crumbled; this library borrows the data structure but points it
somewhere else. Here, the justification structure is not bookkeeping
for retraction — **the explanation is the product**. The deliverable
is the derivation DAG: renderable, queryable, testable.

(That reorientation is also why the library is named **Baskerville**
rather than anything claiming "TMS" — see "What this is not" at the
end, and [`antecedents.md`](antecedents.md) for the full family
history. This library is deliberately *not* Doyle's full non-monotonic
system.)

## Facts are proof terms

If you've spent time with free monads or initial encodings, the kernel
will feel familiar. Here is essentially all of it:

```purescript
data Why rule ax
  = Axiom ax                    -- observed, not derived
  | ByRule
      { rule :: rule            -- which rule fired
      , source :: ax            -- what event triggered the pass
      , premises :: Array FactId -- the facts it consumed
      , anchors :: Array ax     -- non-fact provenance (timestamps, event ids)
      }

type Fact claim rule ax =
  { id :: FactId
  , claim :: claim              -- the statement itself
  , why :: Why rule ax          -- the primary justification
  , alsoWhy :: Array (Why rule ax)  -- every other way it was later rederived
  }
```

All the type parameters are yours. `claim` is your domain's atomic
statements (an ADT with `Ord` — `Is cell digit`, `Lacks player card`,
`Stale node`). `rule` is your rule names (an ADT so a UI can print
them). `ax` is your non-fact provenance — event ids, timestamps, or
just `data Given = Given`.

Read `ByRule` with Haskell eyes: it is a **defunctionalised rule
application**. A rule is morally a function from premises to a
conclusion; instead of applying it and forgetting, we reify the
application as data. The knowledge base is then the free algebra
generated by your rules-as-constructors over your observations-as-leaves.
Every fact is literally a proof term: a node whose children are the
proofs of its premises, bottoming out in axioms.

The free algebra, taken naively, is a *tree* — and proof trees are
exponentially redundant, because the same lemma gets re-proved under
every theorem that uses it. The kernel's one clever move fixes that:

```purescript
addFact :: { claim :: claim, why :: Why rule ax } -> KB ... -> KB ...
```

is **hash-consed on the claim**. The KB is an append-only array of
facts plus an index `Map claim FactId`. The first time a claim
arrives, it gets a fresh `FactId` and its justification becomes the
primary `why`. If the same claim arrives again with a genuinely
different derivation, the fact keeps its place and the new derivation
is appended to `alsoWhy`. So a claim rederivable six ways appears on
the feed **once**, remembering all six — the free tree becomes a
shared DAG, the way `let`-binding shares a subexpression.

Two structural guarantees fall out of the representation, not out of
any algorithm:

1. **Acyclicity by construction.** A derivation's `premises` are
   `FactId`s, and a rule can only cite facts that already exist —
   premises always point at strictly smaller ids. No occurs check, no
   cycle detection; the proof DAG cannot be cyclic because ids are
   issued in feed order. (This covers the primary `why`; `alsoWhy`
   entries may cite later facts and are evidence of rederivability,
   not independently well-founded proofs.)
2. **First justification wins, and rule order is observable spec.**
   Which derivation becomes primary for a multiply-derivable fact is
   decided by which rule fired first — so clients pin their feeds with
   golden tests, the way you'd pin a pretty-printer.

## Saturation: the engine is a Kleene fixpoint

A rule, in its rawest ("prim") form, is just a function:

```purescript
type Derivation claim rule ax =
  { claim :: claim, rule :: rule
  , premises :: Array FactId, anchors :: Array ax }

type Rule res claim rule ax =
  KB res claim rule ax -> Array (Derivation claim rule ax)
```

Look at the KB, emit zero or more conclusions, each citing the facts
it consumed. The engine (`Baskerville.Engine.saturate`) runs every rule, adds
everything they emitted, and repeats until a pass changes nothing.

If that sounds like naive Datalog evaluation, it is — deliberately.
The semantics of the engine is the least fixpoint of monotone rules
over a finite universe, and the termination argument is the classic
one: rules only ever *add* claims, the claim universe is finite, so
the KB ascends a finite lattice and a pass that adds nothing is the
fixpoint. No search, no backtracking, no retraction. The library's
extensions live within this discipline (a semi-naive engine is planned
future work — an invisible optimisation, same fixpoint).

The one entry point most clients use wraps this into a fold:

```purescript
learn :: Engine ... -> KB ... -> { source :: ax, claims :: Array claim } -> KB ...

-- a mind is a fold of learn over a stream of observations:
final = foldl (learn engine) (emptyKB unit) observations
```

Assert an observation's claims as axioms, saturate, repeat. Everything
derived during one saturation is stamped with that observation's
`source` — so the feed records not just *why* each fact holds but
*when it was first noticed*, which is what lets a UI replay the
avalanche of consequences each observation set off.

A pleasant corollary of monotonicity, shipped as `Kernel.subsumes`:
a mind that witnessed a superset of the observations derives a
superset of the claims. If your domain has multiple observers with
different visibility (the library's original client watches a Cluedo
game from several seats), this is the law your perspectives must
satisfy, and it's QuickCheck-able over random streams.

## The rule eDSL: derivations that write themselves

You could write every rule in prim form, and for a few you will (next
section). But prim form has a quiet failure mode: **you** thread the
`FactId`s, and a forgotten citation doesn't crash anything — it just
silently weakens a proof term. The explanation engine's output is only
as honest as its least careful rule author.

So the library's main rule tier is a small eDSL (`Baskerville.Rule`) where
citing is not the author's job. `RuleM` is, in Haskell terms, a stack
you already know:

> ReaderT over the KB × the list monad for nondeterminism × a Writer
> accumulating the premises and anchors each branch touched

concretely `KB -> Array { value, premises, anchors }`, with `Monad`
and `Alternative` instances. The primitives:

| primitive | what it does | what it cites |
|---|---|---|
| `each xs` | enumerate a domain (the list-monad bind) | nothing |
| `matches proj` | scan the feed for claims matching a pattern — one branch per hit | the matched fact |
| `require c` | the claim must already be known (point lookup) | the fact recording it |
| `absent c` | succeed iff the claim is **not** known | nothing (see below) |
| `anchor ax` | attach non-fact provenance to this branch | — |
| `askKB` | read the raw KB | nothing |

The key design point: `matches` and `require` both **test** a claim
and **cite** the fact recording it, in one move. Whatever a rule body
looked at on the way to its conclusion lands in the derivation
automatically. Here is a real rule from the bundled Sudoku client — a
*naked single* (eight digits eliminated in a cell, so the ninth is
placed):

```purescript
rule NakedSingle do
  c <- each allCells
  traverse_ (\d -> absent (Is c d)) allDigits        -- cell not yet placed
  d <- each allDigits
  traverse_ (\other -> require (Not c other))         -- the other eight are
    (Array.filter (_ /= d) allDigits)                 --   eliminated — CITED
  pure (Is c d)
```

Four lines of logic, and the conclusion `Is c d` arrives on the feed
carrying all eight `Not c other` facts as premises — each of which is
itself a fact with its own derivation, recursively, down to the
puzzle's givens. Nobody threaded a `FactId`. The derivation wrote
itself.

### `absent`: negation, carefully

`absent` is **negation as failure**, and it needs the standard Datalog
caveats. "The claim is not on the feed" is only meaningful *at the
fixpoint* — mid-saturation, a claim might simply not have been derived
yet. The classical discipline is stratification: rules that negate a
claim shape must run in a stratum after everything that could derive
that shape has saturated. The library doesn't yet check this
statically (that arrives with the planned analyzable rule tier); for
now the client vouches, and the test kit's oracle (below) catches
violations from outside.

Note also that `absent` cites nothing. This is not an oversight —
there is no fact to cite. Negative knowledge in a monotone system is
knowledge about the *whole feed*, not about any fact on it. It's the
one place a derivation is honestly incomplete, and it's the price of
staying monotone (contrast Doyle's out-lists, at the end).

## The escape hatch: rules that are algorithms

Some inferences are not conjunctive queries, and no eDSL should
pretend otherwise. The canonical example — and the reason the
two-tier design is a load-bearing wall rather than an apology — is
**Régin's alldifferent filtering** (1994), the most famous
algorithm-inside-a-rule in constraint programming:

> an all-different constraint over a set of variables induces a
> bipartite variables↔values graph; build a maximum matching; any
> candidate edge in *no* maximum matching can be eliminated —
> detectable via strongly connected components of the alternating
> digraph.

A full graph algorithm (matching + SCC decomposition) as one inference
step. You cannot write that as a pattern-matching query, and real CP
solvers don't try: they all have exactly this architecture,
declarative constraints plus "global propagators" that are arbitrary
code. Here the escape hatch is just the prim `Rule` type from the
engine section — arbitrary PureScript from KB to derivations, still
scheduled by the same fixpoint, still emitting justified facts. The
Sudoku client ships one (`Sudoku.Rules.ruleAlldifferent`, ~30 lines):
each elimination it emits cites the `Not` facts that shaped the
house's candidate graph, so even the algorithmic tier's conclusions
are explainable — coarser than the eDSL's (a house-level certificate
rather than a minimal one), but honest.

And because the kernel keeps *all* justifications (`alsoWhy`), the two
tiers can prove the same fact in different vocabularies: one
pencil-mark elimination arriving as "hidden single in row 3" from the
human-vocabulary rule *and* "in no maximum matching of this house"
from the algorithm — same fact, one `FactId`, both stories retained.

## Reading the proof back out

`Baskerville.Explain` is the consumer side:

```purescript
explain :: claim -> KB ... -> Maybe (DerivationDag claim rule ax)

type DerivationDag claim rule ax =
  { root :: FactId
  , nodes :: Array (Fact claim rule ax)  -- in feed order, premises first
  , edges :: Array Edge                   -- premise → conclusion
  }
```

`explain` returns the full proof behind one claim: every fact it
transitively rests on and the premise edges among them. Thanks to
acyclicity-by-construction it's a single backward scan over the feed
prefix — no recursion, no visited set. Companions: `axiomsBehind` (the
observation leaves a claim ultimately rests on — "which givens does
this placement actually use?"), `depthOf` (longest premise chain, the
natural stagger order for rendering a cascade), `supporters` (direct
premises, resolved).

The DAG is deliberately plain data — nodes and edges — so it exports
to whatever graph tooling you render with.

## Measuring the engine from outside: ⊢ meets ⊨

Here is the part of the design that has no counterpart in most rule
engines, and the habit most worth stealing.

A rule engine computes what is *derivable* (⊢). Your domain defines
what is *true*: a claim is semantically entailed (⊨) if it holds in
**every** world consistent with the observations. These can disagree
in two directions, and both directions are measurable — because for
the finite universes this library targets, the semantic side needs no
SMT solver. It is *counting*: enumerate the consistent worlds, check
the claim in each.

`Baskerville.Testkit` packages this as an `Oracle` the client supplies —
worlds consistent with the observations, a satisfaction relation, the
claim universe — and two instruments over it:

- **`unsound`** — claims the engine derived that some world refutes.
  For a sound rule set this is empty *always*, and that's a
  property-testable invariant, not a hope.
- **`gap`** — claims true in every world that the engine has *not*
  derived: the completeness gap, as an honest number.

The gap is the interesting one, because monotone saturation is
deliberately not complete — it derives exactly what follows without
search — and the gap makes that a *measurement* rather than a vague
disclaimer. The Sudoku client tells the whole story in miniature, and
it's pinned in `Test.OracleSpec`:

1. The four singles-tier rules solve easy puzzles outright
   (gap = 0 — provably complete on those instances).
2. An oracle-driven hunt found `gapPuzzle`: 22 givens, unique
   solution, where the singles tier stalls at 30/81 cells with a
   183-claim gap. "This puzzle requires more than singles" is now a
   *theorem the library proves about itself*, not folklore.
3. Adding the Régin escape-hatch rule closes it: 81/81, gap = 0,
   soundness intact — and the oracle certifies the closure.

Find the gap, close it with a stronger rule, certify the closure. The
seam is also available pointwise:

```purescript
explainOr :: Oracle world claim -> KB ... -> claim
          -> Either (Refutation world) (DerivationDag claim rule ax)
```

either a proof, or the precise reason there isn't one: a
`Countermodel` (a world where the claim fails — it isn't entailed), or
`Underived` (entailed but beyond your rules — the gap, pointed at one
claim), or `NoWorlds` (your observations contradict each other).

## What this is not: the actual JTMS

Honesty about the name. Doyle's 1979 system — the thing the letters
"JTMS" properly denote — is **non-monotonic**: a justification may
require premises to be *out* (disbelieved) as well as *in*, which
gives you defaults and assumptions ("believe the estimate until
measured"), and with it comes an in/out labelling algorithm with
genuine subtleties (odd loops, unfounded support) plus
dependency-directed backtracking, so beliefs can be *withdrawn* when
their support crumbles.

This library, version 1, is deliberately the **monotone core** of that
tradition: justifications, the shared derivation DAG, saturation —
with no retraction and no non-monotonic labelling. Facts, once on the
feed, stay. The choice is argued at length in the [design
sketch](library-sketch.md) (extensions catalogue, row 6); the short
version is that two cheap mechanisms eat most of full-Doyle's lunch at
none of its structural cost:

- **Retraction by replay.** The KB is a pure fold over an observation
  log. To retract an observation, replay the log without it —
  milliseconds at these KB sizes, and the "facts are proof terms"
  invariant survives untouched. (Counterfactuals fall out free:
  replay with a *different* observation.)
- **Negation as failure.** Much of practical default reasoning is
  "conclude X when there's no evidence of Y", which `absent` handles
  monotonically within a stratum.

The append-only feed is also what keeps the door open to de Kleer's
ATMS (labelling each fact with the assumption sets under which it
holds): recording *all* justifications now (`alsoWhy`) makes that a
retrofit rather than a rewrite.

## Situating it, for the Haskell-adjacent reader

The nearest neighbours in the typed-FP world are the propagator
lineage — Radul & Sussman's *Art of the Propagator*, Kmett's
`propagators` and `guanxi`, Tom Harding's `holmes` (join-semilattice
cells + CDCL, on Hackage). The machinery rhymes: monotone functions
over lattice-ish state, run to fixpoint. The difference is what the
machinery is *for*. That lineage points it at **search** — solve the
puzzle, find the assignment, learn nogoods — and provenance, where it
exists, is internal fuel for the backtracker. This library points the
same machinery at **explanation** and ships the derivation DAG as the
deliverable. No search in the kernel at all; where search-strength
inference is needed, it arrives as an escape-hatch rule (Régin) whose
conclusions are still justified facts, and completeness relative to
full search is measured honestly by the oracle rather than achieved by
backtracking.

Other familiar landmarks: the engine's semantics is textbook Datalog
(naive evaluation, stratified negation); the kernel is the "Free From
Tree" defunctionalisation move (Faubion) applied to *derivation*
instead of sequencing; and hash-consing first-justification-wins is
the same sharing move that turns free-structure trees into DAGs
everywhere else.
